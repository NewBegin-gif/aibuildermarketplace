XSDHub Review: E-Invoices Checked Against the Official Rules, with Proof

XSDHub checks whether an e-invoice follows the official rules before you send it: EN 16931, Germany's XRechnung, France's Factur-X, Poland's KSeF, Romania's RO e-Factura and Croatia's HR-CIUS. Every result names the rule version that judged it. The XML and XSD workbench we reviewed in October is still part of it.

What else it checks now

  • Six e-invoice formats: EN 16931 in UBL and CII, XRechnung 3.0.2, Factur-X 1.09.2, KSeF FA(3), RO e-Factura and HR-CIUS. EN 16931 uses version 1.3.16 through 14 November 2026 and 1.3.17 from 15 November; you can choose the date that applies to your invoice.
  • Public evidence: across its validators, all 41,053 checks against selected official test cases from CEN, KoSIT, the W3C, FNFE-MPE and national tax authorities matched the expected results, checked 9 November 2026. The method is on xsdhub.com/developers.
  • Beyond invoices: SAF-T audit files for Portugal, Norway and Romania (D406), Polish JPK returns, SEPA pain.001 and pain.008 batches with bank profiles for Dutch, German, Belgian and French banks, ISO 20022 camt.053/054 and pacs.008, DAC7, CBAM, XBRL with Arelle and UBL despatch advice.
  • XSDHub follows the official source publications hourly, and the API returns the rule versions with every result.
  • Developers get the validation API, a Python CLI, a GitHub Action and an MCP integration. The site runs in eight languages.

What a pass does not mean

A pass covers the published technical rules of the selected validator. It is not certification, it does not decide your tax status and it does not prove that a recipient or tax portal will accept the invoice. Peppol-specific rules are not checked; the EN 16931 part is. The KSeF check uses the fixed FA(3) schema only, without arithmetic or acceptance checks.

The practical verdict

For e-invoices, XSDHub answers the question that decides whether an invoice comes back: does it follow the rule set the recipient applies, and which version was used? Our 9 November test shows it doing that for a common German failure, with the version on the result. When your problem is a schema rather than an invoice, the XML workbench below is still the right tool.

XSDHub is useful when you have an XML file in front of you and need a specific answer: is it well-formed, does it match this XSD, or can I make it readable? It separates a syntax pass from a schema pass. That distinction matters: a document can be valid XML while its element order, namespace or date format is wrong for the receiving system.

The free workbench needs no account. Paste XML, add an XSD if needed, and run the check. Errors include line information when the underlying engine supplies it. The practical guides load a failing example or its correction into the editor, making them useful for learning the reason for a failure.

We would start with Free and a representative file from your own workflow. Pro makes sense when repeated batches and saved schemas save you time. Team is aimed at a small group using the same schema library. Neither paid plan changes the validation engine or removes the format restrictions.

One example, without the marketing

This is malformed XML. A syntax check is enough to catch it; no XSD is needed.

<order>
  <item>Notebook</itemz>
</order>

The engine reported Opening and ending tag mismatch: item line 2 and itemz. Changing the closing tag to </item> made the same input pass. A pass here confirms syntax only; it does not validate an order's business rules.

What the wider checks covered

At the end of the second audit, 39 automated tests passed. They covered these examples, additional XML edge cases, payment-signature validation, account-linking safeguards, subscription state selection and restricted measurement payloads. Fourteen live HTTP checks verified refusal of anonymous or forged identities, invalid request origins, unsigned payment notifications and malformed measurement requests. These counts are engineering evidence, not a security certification.

Unicode, CDATA and escaped characters passed the syntax tests. Duplicate attributes, unbound namespace prefixes, multiple roots and unknown entities failed. Formatting preserved the tested mixed-content sentence, including its Unicode text. What stays on your device, and what does not

XML syntax checks, schema validation and formatting run in the browser using libxml2 and WebAssembly. XML document contents are not sent to a validation server. Saving a schema is different: that explicit action uploads the XSD to your account, and Team schemas are shared with that workspace.

Account authentication, payments, server requests and limited aggregate usage measurement still involve services outside the local editor. “Local validation” does not mean “the entire website has no network activity.” Read the privacy policy for those boundaries. The AI/MCP endpoint exposes public documentation; it cannot validate documents or read saved schemas. A separate consent-based HTTPS validation API and Python CLI are now documented at xsdhub.com/developers.

The limits we would want to know before paying

  • XSD 1.0 with local dependencies: load XSD files, a folder or a ZIP and choose the main schema. Local imports and includes are supported. Optional server modes add XSD 1.1 and Schematron XPath 1.0 with explicit upload consent. An explicit public HTTPS importer downloads schema dependencies as a snapshot. Private network fetching and DTDs remain blocked.
  • Small inputs: XML inputs allow 10 MB, schemas 1 MB each, and projects 100 schemas / 10 MB total. Paid local batches use two reusable workers; server batches are limited to ten files and the documented request rate.
  • Not a business-rule engine: a schema pass does not prove invoice arithmetic, regulatory compliance or acceptance by your trading partner.
  • Shared library, not a full collaboration suite: Team includes five seats and invitation links. Do not assume real-time co-editing, enterprise SSO or emailed invitations.
  • No automation API for validation: the public MCP service reads guides and capabilities. It does not replace a CI validator.
  • Incomplete checkout safeguards can require support: a pending checkout for a different plan or an uncertain payment state is blocked rather than silently opening a second payment.

Our own audits found and fixed issues around old test subscriptions, duplicate checkout attempts, expired Team membership and linking an account with a pending Paddle checkout. Those fixes are useful evidence of improvement, not a reason to call a new product flawless.

Who should use it, and limits to check

Good fit: developers, integration staff and technical operations teams checking small XML exports against XSD 1.0 schemas, including local multi-file projects, especially when they want a quick browser tool and examples that explain the failure.

Check these limits: if you need inputs above 10 MB, XPath 2.0 Schematron, an enterprise SLA or a validator certified for a specific industry standard. If you only need an occasional syntax check, start with Free; there is no need to subscribe merely to validate one document.

Our conclusion

The strongest part of XSDHub is now the step before you send: an e-invoice checked against the official rules, with the rule version and its source on the result. For schema work, the direct path from a concrete XML error to a corrected example still holds. Its value is a focused, local check with clear limits. Whether the paid library and batches are worth the price depends on how often you repeat that work. Test your actual schema with the free workbench first.
